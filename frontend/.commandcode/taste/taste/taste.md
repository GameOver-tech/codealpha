# Taste
- Never generates demo pages, mock data, placeholder responses, or fake APIs — every feature must consume real backend endpoints and work end-to-end before being considered done. Confidence: 0.95
- Wants design references improved significantly rather than copied verbatim ("improve it significantly, do NOT copy it exactly"). Confidence: 0.9
- Considers a task complete only when it is production-ready and verified end-to-end (typecheck/build pass, dev server boots, backend connectivity confirmed through the proxy). Confidence: 0.85
- Wants explicit handling of all failure modes (404, 500, unauthorized, network/offline, empty data) with loading skeletons, empty states, and dedicated error pages. Confidence: 0.85
- Prioritizes accessibility by default: keyboard navigation, ARIA labels, semantic HTML, and visible focus states. Confidence: 0.85
- Wants surgical, targeted fixes over rewrites: preserve the existing architecture, folder structure, API contracts, and working functionality; only modify what is broken; maintain backward compatibility and avoid breaking changes. Confidence: 0.95
- Requires strict role-based access control enforced on the backend (unauthorized role calls return 403, e.g. candidates blocked from admin upload APIs) plus per-user data isolation — a candidate must only ever see their own interviews/results. Confidence: 0.85
- Expects referential integrity in the data model: all records chained by proper foreign keys (users → profiles → interviews → transcripts/analysis/scores/recommendations/reports/pdfs) with no orphan records. Confidence: 0.8
- Storage discipline: media (video/audio) and generated PDFs must be transient — keep the uploaded file only until processing completes, then delete it (including a startup sweep that purges orphaned media from completed interviews); PDFs are generated on demand in memory from stored results and never persisted to disk/DB. Only the transcript, AI evaluation, scores, and status remain permanently. Confidence: 0.9
- Never re-runs expensive AI work (Deepgram transcription, LLM evaluation) unless the admin explicitly requests "Reprocess Interview"; PDF generation/regeneration and status reads must come only from stored DB results and complete in seconds without touching the AI pipeline. Confidence: 0.85
- Wants the application's data stored in their own hosted Supabase Postgres project (not local Postgres) so they can visually inspect tables and credentials in the Supabase dashboard — they verify new data by watching for it in the Supabase Table Editor and flag any divergence between the schema they see there and where the backend actually writes. Confidence: 0.9
- Reports bugs/data issues by attaching a screenshot of the affected screen (e.g., the Supabase Table Editor) rather than describing the state in text; investigate the visual state directly. Confidence: 0.6
- Uses candidate email as the unique identifier for linking interviews to candidates: admin uploads must require a candidate email, validate the candidate exists (reject unknown emails), and every transcript/score/recommendation/report stays linked to candidate_id + email. Confidence: 0.8
- Wants operational traceability: audit logs for interview upload, transcript generation, AI evaluation, status changes, and PDF generation/regeneration, capturing admin, timestamp, candidate email, and interview ID. Confidence: 0.7
